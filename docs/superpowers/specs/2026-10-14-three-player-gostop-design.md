# 토끼고스톱 3인 게임 프로젝트 분석과 설계 검토본

작성일: 2026-10-14. 분석 기준: 복제 폴더의 HEAD `7e241a3`.

결정 갱신: 2026-10-15. 상태: 요구사항 결정 완료, 통합 설계 검토용.

토끼맞고 복제본을 기반으로 독립적인 토끼고스톱을 만든다. 첫 출시 모드는 혼자 치기(사람 1명 + AI 2명)와 친구와 치기(사람 3명)이며, 신뢰하는 가족·친구를 위한 방장 브라우저 판정 구조를 유지한다. 게임머니 없이 승자 가산·패자 차감의 순점수를 기록한다.

새 공개 저장소는 `GNOJES/toki-gostop`이며 기존 Git 이력을 보존한다. Firebase·DB·Vercel·접속 주소·GA 통계를 맞고와 분리한다. 제품 정책은 9절의 사용자 확정 결정표를 기준으로 하며, 구현 모듈과 검증 경계는 6~10절에서 제안한다. 저장소·클라우드 개설과 제품 코드 구현은 아직 진행하지 않았다.

현재 원격 `origin`은 `https://github.com/GNOJES/toki-matgo.git`이다. 폴더 이름만 달라졌으며 저장소 독립은 아직 완료되지 않았다. 분석 시작 시 추적 파일의 작업 트리는 깨끗했다.

## 3. 독립 저장소와 운영 분리

확정한 D01-1에 따라 제품명은 **토끼고스톱**, 저장소 이름은 `toki-gostop`이다. 앱 제목·설치 이름·공유 화면에도 토끼고스톱을 사용한다. D01-3에 따라 새 저장소의 대상은 `GNOJES/toki-gostop`, 공개 범위는 공개로 확정했다. 실제 저장소 생성과 원격 연결은 구현 단계에서 진행하며 아직 실행하지 않았다.

확정한 D17-1에 따라 고스톱 전용 Firebase 프로젝트·Realtime Database·Vercel 프로젝트·접속 주소를 별도로 구성한다. 원본 맞고와 인증·방 데이터·보안 규칙·배포 설정을 공유하지 않는다. 실제 프로젝트 개설과 연결은 구현 단계에서 진행한다.

1. 확정한 D01-2에 따라 기존 맞고의 Git 커밋 이력을 보존한다. 새 저장소 생성 후 이 복제본의 원격을 새 주소로 연결하여 독립 운영한다. 원본에 작업을 push하지 않도록 최종 원격 확인을 분리 완료 조건으로 둔다. Git 이력을 초기화하지 않는다.
2. Firebase 프로젝트와 RTDB를 새로 분리한다. 원본 방 데이터·익명 사용자·Rules를 공유하지 않는다. 개발/CI 에뮬레이터 식별자도 새 `demo-…` 값으로 변경한다.
3. Vercel 프로젝트·운영 도메인·환경변수도 분리한다. 복제된 `.env.local`이나 `.vercel` 연결 정보를 그대로 운영에 사용하지 않는다. 존재 여부와 대상 프로젝트를 구현 착수 시 확인하되 비밀값은 문서나 로그에 기록하지 않는다.
4. `scripts/validate-env.mjs`의 현재 검증은 Firebase 설정끼리의 일치만 확인한다. 새 앱에서는 원본 프로젝트 ID를 거절하고 승인된 새 프로젝트 ID를 검증한다. 원본 설정도 서로 일치하므로 현재 검증만으로 분리를 보장할 수 없다.
5. `package.json`, README, metadata와 공유 이미지, manifest, 앱 아이콘의 제품 표기와 운영 주소를 새 게임에 맞춘다.
6. 설정·방 복구·기록·분석 중복 방지 키와 IndexedDB 이름, SW 캐시 접두사를 새 제품 namespace로 바꾼다. 기존 기록은 기본적으로 가져오지 않는다. 서로 다른 도메인이 저장소를 분리하더라도 앱 구분을 명시한다.
7. SW 생성 스크립트와 `public/sw.js`를 함께 변경한다. 새 SW가 맞고 캐시를 자기 캐시로 판단하여 삭제하거나 옮기지 않도록 한다. PWA는 별도 origin 운영을 추천한다.
8. 확정한 D17-2에 따라 첫 출시부터 맞고와 별도 GA 스트림으로 통계를 수집한다. 방문과 게임 시작·종료, 방 생성·참가를 집계하며 닉네임·방 코드·손패는 전송하지 않는다. 기존 코드의 맞고 운영 호스트와 GA ID 기본값을 새 스트림·ID·운영 호스트로 변경한다. Preview·개발·디버그·오프라인에서는 기존처럼 통계 수집을 비활성화한다. 개인별 플레이 기록 저장과는 별개다.
9. 카드 출처·변경 내역·배포 라이선스 표시는 기존 `docs/ASSETS.md`와 `public/cards/LICENSE.txt`의 관리 방식을 보존한다.

저장소 생성·원격 변경·클라우드 프로젝트 생성·배포는 이번 분석 작업에서 실행하지 않았다.

## 4. 첫 출시 범위

사용자 결정 D02에 따라 **혼자 치기: 사람 1명 + AI 2명**, **친구와 치기: 사람 3명**으로 확정했다. 친구 2명 + AI 1명인 혼합 모드는 첫 출시에서 제외한다. 혼합 모드를 추후 추가하려면 AI 판정 주체·이탈 시 대체·다음 판 합의·방장 단절 정책을 별도로 설계한다.

확정한 제품 대상은 신뢰하는 가족·친구이며 게임머니·베팅 없이 순점수로 기록한다. 모바일 세로 화면과 기존 토끼 디자인을 유지한다. 기존에 없는 공개 매칭·관전·계정 랭킹은 이번 설계에 추가하지 않는다. 자동 방장 교체는 D15-1에 따라 제외한다. 기존 혼자 치기의 PWA 오프라인 기능과 난이도 선택은 재사용하며, 두 AI 모두 자신의 개인별 뷰만 보고 판단하도록 변경한다.

## 5. 게임 규칙 설계

### 기준과 출처

아래 한게임 **3인 고스톱 안내**는 설계 당시 차이점을 확인한 참고 자료다. 실제 제품 규칙은 사용자 결정 D01~D18과 기존 맞고의 기본 족보를 조합한 토끼고스톱 규칙이다. 참고 자료와 사용자 결정이 다르면 사용자 결정이 우선한다.

- [고스톱의 기본](https://hangame-images.toastoven.net/hangame/pc/gostop/introduce/html/ssgostop/guide_ssgostop03_01.html): 세 명 각 7장, 바닥 6장, 안내의 전체 패는 51장. 첫 판 방장 선, 이후 승자 선.
- [고스톱의 기본2](https://hangame-images.toastoven.net/hangame/pc/gostop/introduce/html/ssgostop/guide_ssgostop03_02.html): 3점부터 고/스톱, 첫뻑/2연뻑/3연뻑 3/6/9점, 누적 3뻑 3점 종료, 첫따닥 3점. 자뻑 안내는 피 한 장으로 기재되어 있다.
- [점수계산법](https://hangame-images.toastoven.net/hangame/pc/gostop/introduce/html/ssgostop/guide_ssgostop03_03.html): 패자 피 5장 이하의 피박, 독박의 부담 이전, 총통 5점, 허당 3점. 폭탄은 상대들에게 각각 피 1장.

보너스 2장, 0피 피박 면제, 자뻑 각 2피, 연속 나가리 배수 누적, 허당 제외와 무작위 첫 선은 아래 사용자 결정대로 적용한다. 참고 서비스와 동일한 세부 규칙이라고 취급하지 않는다.

### 확정한 분배와 기본 진행 및 보너스 처리

확정한 D05에 따라 기본 48장 + 쌍피 보너스 2장 = **50장**을 사용한다. 각 보너스는 2피이며, 한게임 안내의 51장과는 다른 앱 정책이다. D06에 따라 각자 손 7장, 바닥 6장으로 분배하며 보너스 처리 전 초기 덱은 23장이다.

확정한 D06a의 보너스 기본 처리: 바닥 보너스는 선이 가져가고 일반패 6장이 될 때까지 보충한다. 손 보너스는 기존처럼 낸 뒤 덱에서 손패를 보충하고 차례를 이어간다. 덱 보너스는 획득 후 추가 뒤집기한다. 보너스 자체로 상대 피를 가져오지는 않는다. 확정한 D12-3에 따라 같은 뒤집기 과정에서 보너스가 나온 뒤 뻑이 발생하면 해당 보너스는 뻑 더미에 붙이고, 나중에 그 뻑을 먹는 사람이 함께 획득한다. 손에서 내어 이미 획득한 보너스에는 영향을 주지 않는다.

세 자리의 정규 턴은 각 7회다. 보너스 교체는 정규 턴을 쓰지 않고 폭탄은 패스 권리 2회를 준다. 보너스가 손패 보충·추가 뒤집기로 처리되므로 기본패 48장은 손에서 낼 일반패 21장 + 초기 바닥 일반패 6장 + 정규 뒤집기 일반패 21장으로 보존된다. 총 카드 수는 선택한 덱 구성에서 유도하여 검증하며 기존 50장 상수를 그대로 남기지 않는다.

좌석 순서는 `0 → 1 → 2 → 0`으로 고정하며 선부터 시작한다. 물리적인 진행 방향은 UI 상대 배치와 맞춰 안내한다. 남은 정규 턴이 없는 좌석은 건너뛰고 모두 소진하면 나가리다. 손패 장수만으로 마지막 턴을 판단하지 않는다.

점수 3점 이상이며 자신의 이전 고 선언 점수를 넘으면 고/스톱을 선택한다. 확정한 D12-5에 따라 자기 마지막 정규 턴을 마쳤을 때 이 조건을 충족하면 고 선택 없이 자동 스톱한다. 조건 미충족이면 남은 사람의 차례를 계속하고, 전원 턴 소진까지 승자가 없으면 나가리다. 마지막 턴의 국진 선택이 필요하면 먼저 선택한 뒤 점수를 판정한다.

확정한 D12-6에 따라 국진은 획득 시 기본 열끗이며, 자기 차례에 패를 내기 전에 쌍피로 전환할 수 있다. 정규 턴 종료 후 쌍피 전환으로 고·스톱 조건을 충족할 수 있으면 열끗 유지/쌍피 전환을 먼저 묻는다. 쌍피로 전환한 뒤에는 열끗으로 되돌릴 수 없다. 패를 내기 전 전환으로 고·스톱 조건을 충족하여 고를 선택하면 아직 패를 내지 않았으므로 자기 차례를 계속한다. 전환한 국진은 피 이동 대상이며, 다른 사람에게 이동해도 쌍피 상태를 유지한다.

### 기본 족보와 흔들기·폭탄

D18에 따라 기본 족보는 기존 `src/game-engine/score.ts`와 카드 metadata를 유지한다.

| 족보 | 기본 점수 |
| --- | --- |
| 광 | 3광 3점, 비광 포함 3광 2점, 4광 4점, 5광 15점 |
| 열끗 | 5장 1점, 이후 1장당 +1점. 쌍피 전환 국진 제외 |
| 고도리 | 2·4·8월 고도리 열끗 3장 +5점 |
| 띠 | 5장 1점, 이후 1장당 +1점 |
| 홍단·청단·초단 | 각각 완성 시 +3점. 비띠는 초단 제외 |
| 피 | 10피 1점, 이후 1피당 +1점. 쌍피·보너스는 각 2피 |

손에 같은 월 3장이 있고 바닥에 그 월이 없을 때 흔들기를 선택할 수 있다. 공개한 흔들기 1회당 일반 승리 배수 ×2이며 같은 월에는 한 번만 선언한다. 손 같은 월 3장과 바닥 나머지 1장을 먹는 폭탄도 일반 승리 배수 ×2이고 이후 패스 권리 2회를 준다. 흔들기·폭탄 횟수에 따른 배수는 곱한다. 피 이동은 D10, 마지막 턴 예외는 D12, 총통·3뻑의 배수는 D11-3을 우선 적용한다. 미션·이벤트 배수·2장 폭탄은 추가하지 않는다.

### 점수와 정산 분리

기존 `finalScore` 하나로는 두 패자의 서로 다른 배수를 설명할 수 없다. 다음 세 단계를 분리한다.

1. 개인 족보와 기본점수를 계산한다. 이 계산은 다른 사람의 상태에 의존하지 않는다.
2. 승자의 고·흔들기·폭탄·멍따·이월된 나가리 등 공통 요소로 승리 기준점을 만든다.
3. 각 패자의 피박·광박을 계산해 개별 부담액을 만든 뒤 고박/독박 책임 이전을 적용한다.

확정한 D09-1의 고 반영 점수는 `(기본점수 + min(고횟수, 2)) × 2^max(고횟수−2, 0)`이다. 기본점수 5에 3고라면 14점이며, 여기에 다른 배수를 적용한다.

확정한 D08-1에 따라 피박은 승자의 피 점수가 1점 이상이고 해당 패자의 피가 1~5피인 경우에만 ×2다. 0피와 6피 이상은 면제한다. 두 패자를 독립적으로 판정하며 카드 장수가 아닌 피 단위로 계산한다.

확정한 D08-2에 따라 광박은 승자의 광 점수가 있을 때 해당 패자가 광 0장이면 ×2다. 비광 포함 3광도 승자의 광 점수에 포함한다. 패자 광 1장 이상은 면제이며, 피박과 중복되면 ×4다.

확정한 D08-3에 따라 승자 열끗 7장 이상이면 멍따 ×2를 두 패자에 공통 적용한다. 패자의 열끗 장수에 따른 면제는 없다. 쌍피 전환 국진은 열끗에서 제외하고 피박·광박과 중복되는 배수는 곱한다.

확정한 D04의 기록 방식은 **세 사람의 순점수 변화 합계가 0**이 되는 정산이다. 현재 맞고는 승자 점수 및 즉시점수 누적이며 패자 차감이 없으므로 이 부분은 제품 정책 변경이다. 게임머니와 무관한 점수다. 음수 누적 점수를 허용한다. UI에는 획득·부담·순변화를 함께 표시하는 안을 추천한다.

예: 승자 A의 공통 기준점 6, B만 피박이면 B 부담 12, C 부담 6이다. 최종 변화는 A +18 / B −12 / C −6. B가 독박 책임자라면 B가 18을 부담하고 C는 0이다. **D09-2에 따라 독박 부담 이전에 기존 맞고식 고박 ×2를 다시 곱하지 않는다.**

확정한 D11-1에 따라 자기 첫 정규 턴의 첫뻑은 두 상대에게 각각 3점, 첫 턴부터 연속한 2번째 뻑은 각각 6점 추가, 3번째 뻑은 각각 9점 추가를 받는다. 자기 첫 정규 턴의 첫따닥은 두 상대에게 각각 3점을 받는다. 이 즉시 점수에는 배수를 적용하지 않으며 누적한다. 누적 3뻑에 따른 판 종료 점수는 별개다.

즉시점수도 `받는 사람의 가산`만 기록하지 않고 지급자별 거래로 기록한다. 첫뻑 3점씩을 두 명에게 받으면 해당 플레이어 +6, 나머지 각 −3이다. 이후 누가 이기든, 나가리가 되든 이미 확정된 즉시 거래를 유지한다. 판 종료 때 즉시 거래를 다시 더하지 않도록 거래 ID와 정산 완료 식별자를 둔다.

확정한 D09-2의 독박은 가장 최근 고 선언자 한 명을 책임 후보로 기록하고, 다른 사람이 고하면 후보를 바꾸며, 다른 사람이 일반 스톱하면 두 패자의 부담 합을 후보에게 이전한다. 각 패자 기준으로 피박·광박 등 배수를 먼저 계산한 뒤 부담을 합친다. 독박으로 추가 ×2를 적용하지 않는다. 후보가 승리하면 이전하지 않으며 고 선언자가 없으면 각 패자가 자기 부담을 낸다. 자기 차례가 돌아오거나 다음 자기 턴을 끝내도 책임은 유지한다. 총통·3뻑의 특수 종료에는 적용하지 않는다. 예를 들어 A 고 → B 고 → C 스톱이면 B가 A와 B의 부담을 모두 내며, A 고 → A 스톱이면 독박 없이 B와 C가 각각 낸다.

확정한 D11-2의 특수 승리는 초기 손패에 같은 월 4장이 있는 총통(각 패자 5점)과 한 판에 누적 3회 뻑을 하는 3뻑(각 패자 3점)이다. 3뻑은 연속 여부와 무관하다. 허당 승리는 제외하여 연속 5회 패를 먹지 못해도 이 조건으로 판을 끝내지 않는다. 첫뻑 등 이미 발생한 즉시 거래는 별도로 보존한다.

확정한 D11-3에 따라 총통·3뻑의 고정점에는 이월된 나가리 배수만 적용한다. 피박·광박·멍따·고·흔들기·폭탄은 적용하지 않으며, 독박도 D09-2에 따라 제외한다. 나가리 ×2 상태라면 총통은 상대별 10점, 3뻑은 상대별 6점이다. 첫뻑 등 즉시 점수에는 이 배수도 적용하지 않는다.

확정한 D13에 따라 연속 나가리 횟수가 n이면 다음 판의 승리 정산 배수는 2^n이다. 나가리 1회 후 ×2, 2회 연속 후 ×4, 3회 연속 후 ×8로 누적한다. 일반 승리와 총통·3뻑에 적용하며 첫뻑 등의 즉시 거래는 제외한다. 승패가 확정된 다음 판은 연속 횟수를 0으로 초기화하여 ×1로 돌아간다. 동시 총통·초기 바닥 같은 월 4장에 따른 재분배는 연속 나가리 횟수와 배수를 바꾸지 않는다.

확정한 D12-1에 따라 초기 손패에서 두 명 이상이 동시에 총통이면 승패·점수 없이 같은 선·같은 판 번호로 다시 섞어 분배한다. 새 나가리 배수는 만들지 않고 이전 판에서 넘어온 나가리 배수는 유지한다. 재분배 대상의 손패·바닥·덱·초기 보너스 획득은 모두 폐기하고 새 분배로 구성한다.

확정한 D12-2에 따라 최초 바닥의 일반패 6장에 같은 월 4장이 있으면 점수 없이 같은 선·같은 판 번호로 다시 섞어 분배한다. 시작 보너스 획득 내역도 되돌린다. 새 나가리 배수는 만들지 않고 기존 나가리 배수는 유지한다. 보너스를 일반패로 보충한 뒤 같은 월 4장이 구성된 경우에도 같은 검사를 적용한다.

### 피 이동과 마지막 턴

확정한 D10-1에 따라 쪽·따닥·쓸·폭탄은 상대 두 명에게 각각 1피 단위를 요청한다. 대상에게 피가 없으면 그 대상만 건너뛰고 다른 사람에게 부족분을 추가 요청하지 않는다. 같은 턴에 여러 효과가 발생하면 요청량을 합산한다. 마지막 턴에는 확정한 D12-4 예외를 적용한다.

확정한 D10-2에 따라 남의 뻑을 먹으면 두 상대에게 각각 1피, 자뻑을 먹으면 두 상대에게 각각 2피를 요청한다. 피가 없는 상대는 건너뛰며 부족분 대납은 없다.

사용자가 확정한 D10-3의 전체 공통 규칙은 카드 장수가 아닌 피 단위로 이동량을 계산하는 것이다. 홑피는 1피, 쌍피는 2피다. 1피 요청에도 쌍피 한 장만 보유했다면 그 한 장을 이동한다. 2피 요청에는 쌍피 한 장으로 충족하며 두 장을 요구하지 않는다. 2피 요청에 홑피 한 장만 보유했다면 그 한 장만 이동하고 부족분은 남기지 않는다. 피가 없으면 이동하지 않는다. 카드를 쪼개거나 초과분을 돌려주지 않는다. 같은 턴 합산 요청에도 같은 계산을 적용한다.

확정한 D10-3a에 따라 홑피부터 자동으로 이동하고, 요청 피 단위를 채우지 못했을 때 쌍피를 이동한다. 요청량이 2피이고 홑피 2장과 쌍피 한 장이 있다면 홑피 2장을 준다. 요청량이 2피이고 홑피 한 장과 쌍피 한 장이 있다면 홑피 한 장을 먼저 준 뒤 쌍피 한 장을 주어 실제 3피가 이동한다. 카드 분할과 초과분 반환은 없다. 이벤트는 출발 자리·도착 자리·실제 카드·요청 피 단위·실제 이동 피 단위를 담고 두 상대의 이동을 구별한다. 확정한 D12-6에 따라 국진은 쌍피 전환 후에만 이동 대상으로 삼으며 이동 후에도 쌍피 상태를 유지한다.

확정한 D12-4에 따라 마지막 자기 정규 턴에는 뻑 모양이 나와도 뻑을 쌓지 않고 바닥패와 낸 패를 획득한 뒤 뒤집은 패는 바닥에 둔다. 쪽 모양은 두 패를 획득하되 피를 가져오지 않고, 따닥도 네 패를 획득하되 피를 가져오지 않는다. 쓸도 바닥패 획득만 하고 피를 가져오지 않는다. 기준은 손패 장수가 아닌 폭탄 패스까지 포함한 자신의 마지막 정규 턴이다. 한 턴의 여러 효과는 적용 가능한 요청량을 합산한다. 확정한 뻑 회수 대상과 피 단위 계산, 마지막 턴 예외는 규칙서에 명시하고 시나리오로 검증한다.

권위 상태 → 행동 검증 → 새 상태/이벤트 → 개인별 projection → 연출 → 완료 확인 순서를 유지한다. UI 상태로 승패를 계산하지 않는다. AI도 전체 상태나 미래 덱을 받지 않는다. 점수 정산 결과에는 패자별 원래 부담·실제 지급자·적용 배수·거래 목록·세 자리 순변화를 담는다.

연속 나가리 배수에 임의 상한을 추가하지 않는다. 큰 누적 점수도 정확히 보존하도록 정산·누적 점수는 BigInt로 계산하고 Firebase JSON·브라우저 저장에는 부호 있는 10진 문자열로 직렬화하는 설계를 사용한다. 개인 족보와 카드 장수는 기존 number를 유지한다.

서로 다른 서버 구조를 선택해도 순수 엔진과 개인 뷰 계약은 유지한다. 선택한 신뢰형 Firebase에서는 DB 참가자가 전체 상태를 읽을 수 있으므로 개인 뷰가 DB 수준의 비밀 패 보호를 제공한다고 설명하지 않는다.

## 7. 3인 방과 동기화

### 운영 구조 선택

| 구조 | 적합한 경우 | 영향 |
| --- | --- | --- |
| 방장 브라우저 판정 + 별도 Firebase | 신뢰하는 가족·친구, 기존 운영 유지 | **D03 확정**. 전체 상태 공개와 방장 단절 시 중지라는 기존 한계를 유지 |
| 서버 판정 + 사용자별 비밀 뷰 | 공개 매칭·랭킹·치팅 방지, 방장과 무관한 진행 | 별도 서버 수명·비밀 저장·운영 비용·복구 설계를 먼저 확정해야 함 |

공개 경쟁을 원하면 첫 번째 구조에서 출발한 뒤 UI로 손패만 감추는 방식으로 해결하지 않는다. Firebase 사용자별 뷰만 분리해도 방장 브라우저가 판정하는 한 방장 조작 문제는 남는다.

### 좌석과 대기실 추천안

`meta.hostUid`는 관리 권한, 별도의 좌석 집합은 `0/1/2 → UID`를 보관한다. 0번은 방장, 1·2번은 참가 순서대로 배정한다. 방장과 선은 다른 사람일 수 있다. 세 자리 인원과 UID 유일성을 상태 조건으로 검증한다.

두 게스트의 동시 입장은 좌석 집합을 대상으로 하는 트랜잭션으로 하나씩 빈 자리를 배정한다. 좌석마다 독립 선점만 하면 같은 UID가 두 자리를 차지할 수 있으므로 집합 전체의 UID 중복도 차단한다. 참가 권한은 현재 Rules의 단일 `guestUid` 비교를 새 모델에 맞게 다시 작성하며, RTDB Rules의 상위 읽기/쓰기 허용이 하위 제한을 무력화하지 않도록 권한 경계를 검증한다.

방 코드/초대 링크/QR은 유지 추천. 확정한 D14-1에 따라 세 번째 사람이 연결되어 세 명의 좌석·이름·접속이 모두 준비되면 첫 판을 자동 시작한다. 별도 준비 버튼이나 방장 시작 버튼은 사용하지 않는다. 시작 판정은 방장 브라우저가 수행하며 첫 선은 D07의 무작위 추첨으로 정한다. 시작 후 좌석을 고정한다. 네 번째 사람은 거절하며 동일 UID 재입장은 자기 자리로 복귀한다.

확정한 D14-2에 따라 첫 판 시작 전 게스트가 명시적으로 나가면 자리를 반환하여 다른 사람이 참가할 수 있고, 방장이 나가면 방을 종료한다. 게임 시작 후에는 결과 화면에서도 누구든 명시적으로 나가면 방을 종료하며 다른 사람이나 AI로 교체하지 않는다. 진행 중 판에는 기권 승패·종료 점수를 만들지 않고 이미 확정된 즉시 거래와 완료한 판의 기록은 유지한다. 새로고침·일시 단절은 명시적 나가기와 구분한다. 동시 참가나 이탈과 자동 시작이 겹칠 때도 최신 좌석·이름·접속 조건을 검사하고 중복 판 생성을 막는다. 첫 판 자동 시작과 매 행동 뒤 연출 완료 신호, 다음 판 합의는 서로 구분한다.

### 행동과 복구

행동의 판 번호·플레이어별 순번·게임 버전을 유지한다. 세 명의 receipt·processed·통계·nextReady를 관리한다. 현재 버전 연출 완료는 **세 명 모두**로 확장한다. 한 명의 오래된 완료 신호가 새 판/버전을 열지 않도록 한다.

확정한 D15-1에 따라 누구든 일시적으로 연결이 끊기면 모두 판정을 멈추고 복귀를 기다린다. 같은 브라우저·익명 계정으로 복귀하면 자기 자리의 최신 상태로 복구한다. 남은 화면에 끊긴 사람 목록을 표시하며, 복귀 시 과거 연출을 건너뛴 뒤 현재 버전 완료를 보낸다. 2분 후 남은 사람은 기다림을 끝내고 방을 종료하거나 계속 기다릴 수 있다. 자동 패배·자동 방장 교체·AI 대체는 하지 않는다. 종료 시에도 이미 확정된 즉시 거래와 완료한 판의 기록은 유지하며 미완료 판의 승패·종료 점수는 만들지 않는다.

확정한 D15-2에 따라 패 내기·먹을 패 선택·국진 선택·고/스톱에는 제한시간을 두지 않는다. 연결을 유지한 채 아무 행동을 하지 않아도 자동 행동이나 무응답에 따른 패배 처리를 하지 않는다. 연결 단절 시 2분 대기 안내와 선택 제한시간은 별개다.

확정한 D14-3에 따라 친구방은 세 명 모두 ‘한 판 더’를 선택하면 다음 판을 시작한다. 혼자 치기는 사람이 선택하면 시작하고 두 AI는 자동 동의한다. 다음 판 생성 시에는 참가자 연결 상태를 확인하며 일시 단절에는 D15-1을 적용한다. 첫 판의 세 명 연결 시 자동 시작 정책은 유지한다. 다음 판 선은 D07a에 따라 직전 판 승자, 나가리이면 기존 선 유지로 확정했다. D14-4에 따라 방은 생성 후 24시간 유지하며 활동에 따른 연장은 없다. 만료 시 게임 중이어도 방을 종료하고 새 방이 필요하다. 만료로 미완료 판의 승패·종료 점수를 만들지 않으며, 확정된 즉시 거래와 완료 기록은 유지한다.

## 8. 화면과 플레이 기록

확정한 D16-1에 따라 기존 토끼 캐릭터·화투 그림·색감·소리·연출을 유지하고 모바일 세로 화면을 3인용으로 재배치한다. 하단은 나의 획득패와 손패 7장, 상단은 상대 두 명의 작은 패널, 중앙은 공유 바닥과 덱이다. 모바일 가로 화면의 별도 최적화는 첫 출시 범위에 포함하지 않는다. 손패는 작은 화면에서 4+3 배치를 추천하되 세부 배치와 카드 크기는 실제 작은 화면에서 확인하며 조정한다. 상대별 이름·기본점수·고 횟수·남은 패·연결·현재 차례를 구별하고 획득패는 요약과 확대 보기로 제공한다.

모든 기기에서 나는 하단이고 다른 두 자리는 고정된 상대 순서로 배치한다. 화면의 좌우 위치를 엔진의 자리 ID로 취급하지 않는다. 차례 표시·안내·피 이동 애니메이션은 실제 자리 매핑을 사용한다. 고/스톱과 국진 선택 안내는 선택 중인 사람 이름을 표시한다.

바닥과 카드 자산·확대·속도·소리·진동·뒤로가기 보호·중단된 연출 취소는 재사용한다. 상단 패널 때문에 중앙 높이가 줄어드는 경우를 실제 작은 모바일 화면으로 검증한다. 상대 두 명에서 가져오는 피는 각각 원래 카드 위치에서 나의 영역으로 이동한다.

결과에는 승자, 개인 족보, 패자별 피박/광박, 독박에 따른 책임 이전, 즉시 거래, 세 사람의 판 점수 변화와 누적 점수를 표시한다. 승자와 비교한 단일 점수 차이 문구는 제거하거나 세 사람 요약으로 바꾼다.

확정한 D16-2에 따라 플레이 기록은 기존 맞고와 분리하여 현재 브라우저에 저장한다. 최근 완료한 판은 100개까지 보관하고, 혼자 치기의 누적 승패·순점수는 목록 제한과 별도로 유지한다. 친구방에서는 세 사람의 방 누적 점수와 판별 변화를 표시한다. 기기 간 동기화와 기존 맞고 기록 이전은 하지 않으며 브라우저 데이터 삭제 시 기록도 사라진다. 중단한 판은 완료 기록에 포함하지 않고 이미 확정된 즉시 거래는 별도 보존한다. 완료 판 저장 시 해당 즉시 거래를 중복 반영하지 않는다.

기록은 게임 모드, 세 참가자 이름, 나의 자리, 승자, 종료 이유, 규칙 버전, 세 자리 순변화, 판 식별자를 보관한다. 멀티 판 식별자는 재사용 가능한 방 코드만으로 만들지 않고 방 생성 식별자 + 판 번호를 포함한다. 새로고침·다중 탭·중복 수신에도 같은 판을 한 번만 저장한다. 독박 면책자는 점수 0인 패자일 수 있으므로 승패와 부담을 분리해 표시한다.

## 10. 단계별 구현 순서와 완료 기준

다음은 설계상의 작업 순서다. 이 설계 검토 후 구체적인 인터페이스와 테스트 기대값을 담은 실행 계획을 작성한다.

1. **독립 앱 기반**: 새 원격·운영 연결·제품 표기·저장 namespace·환경 검증을 분리. 완료 기준은 원본 저장소/DB/GA로 쓰거나 배포되는 경로가 없는 것.
2. **3인 엔진과 정산**: 세 자리 분배·턴·피 이동·고/스톱·특수 종료·패자별 거래를 구현. fixture로 전체 진행이 가능하고 카드 보존 및 정산 합계가 확인되는 것.
3. **혼자 치기와 3인 화면**: 선택된 플레이 모드에 따라 두 AI와 presenter·판·결과·기록을 연결. 한 판과 다음 판을 모바일에서 끝까지 플레이할 수 있는 것.
4. **3인 친구방**: 좌석 트랜잭션·Rules·연출 완료·동시 참가·재접속·세 명 다음 판 합의를 연결. 세 개의 독립 인증 세션이 같은 상태/정산을 보는 것.
5. **출시 검증**: 타입·단위·Firebase Rules/SDK·모바일 E2E·프로덕션 PWA와 실제 세 기기 확인. 새 운영 연결을 확인하고 새 도메인에서 배포 검증.

확정한 D02에 따라 3단계에 두 AI 구현을 포함한다. D03에 따라 별도 판정 서버를 만들지 않고 방장 브라우저와 Firebase를 사용한다.

### 필수 검증 시나리오

- 각 자리에서 선이 되어 7회씩 순환, 폭탄 패스·연속 보너스 포함 카드 중복/유실 없음. 모든 phase의 보류 카드 포함 보존.
- 3점 경계, 이전 고 점수 미갱신, 피를 빼앗겨 점수 하락 후 회복, 마지막 턴, 국진 수동 전환 전후의 고/스톱.
- 서로 다른 두 패자의 피박·광박, 0피·쌍피만 있는 경우, 뻑 소유자가 제3자인 경우, 한쪽만 피가 없는 경우.
- 1~5피 피박·0피 면제, 자뻑 상대별 2피, 홑피 우선으로 2피 요청에 홑피+쌍피가 이동하는 경우, 허당 미발생 검증.
- 연속 나가리 ×2/×4/×8, 승패 후 ×1 복귀, 재분배 배수 유지, 큰 배수의 정수·직렬화 정확성.
- A 고 → B 고 → C 스톱, A 고 → A 스톱, 고 뒤 특수 종료, 동시 총통, 연속 나가리. 확정한 책임 정책과 배수만 적용.
- 즉시 거래 후 나가리, 종료 수신 반복, 다음 판 중복 요청. 모든 거래의 지급/수령 합계 0, 중복 정산 없음.
- 두 게스트 동시 입장, 같은 UID 복수 탭, 네 번째 참가자, 대기 이탈과 시작 경쟁. 중복 좌석·과잉 참가·중복 판 생성 없음.
- 2번 자리의 유효 행동, 타 UID의 행동·좌석 변경·state 쓰기 거절, 비참가자 방 전체 조회 거절. 승인되지 않은 데이터 경로도 거절.
- 세 명 중 하나의 미완료 연출·단절·새로고침·복귀, 방장 단절, 여러 명 동시 단절, 오래된 ready/행동, 세 명 다음 판 합의.
- 본인 자리가 서로 다른 세 화면에서 상대 이름·차례·피 이동 출발지·결과·순점수 일치.
- 짧은 세로 화면에서 바닥/손패/안내/결정 버튼 접근, 뒤로가기·확대·애니메이션 복구, 오프라인 혼자 치기.
- 다중 탭 기록 저장, 음수 순점수 검증, 같은 방 코드 재사용, 새 앱 캐시가 기존 앱 캐시에 영향을 주지 않음.

## 11. 분석의 범위

소스·운영 문서·Rules·CI와 설치된 Next.js의 PWA/환경변수 안내를 읽어 구조를 확인했다. 이번 변경은 설계 문서뿐이며 실행 테스트·실제 서비스 접속 검증은 수행하지 않았다. README의 검증 이력은 현재 분석에서 새로 실행한 결과로 취급하지 않는다.

D01~D18의 제품 결정은 모두 반영했다. 이 통합 설계의 검토 다음 단계는 데이터 계약·트랜잭션 경계·거래 저장·검증 사례를 구체화한 구현 계획이다.
